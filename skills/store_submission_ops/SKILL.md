# ストア提出実行

## 概要（発動条件と3点セットの位置づけ）

- 素材パックを使って、各ストアへ実際に提出を進める専用スキル。「申請して」「提出を進めて」「ストアに出して」「リジェクトが来た」で使う。

- 3点セットの3番目として使う。前提は store_review_readiness の判定が「提出可能」または「直せば提出可能」の必須項目が解消済みであることと、store_listing_pack のパック状態が不足なし（または不足の影響をユーザーが理解して進める判断をした）こと。

## 連携と自動継続（前提が欠けたら、自分で前段を回す）

- スキルは自動で互いを呼び出す仕組みではない。連携は、この節の指示に従って前段のスキルの SKILL.md を読み、その指示で不足を埋めてから戻ることで成立させる。

- 前提が崩れている場合は、ユーザーへ差し戻して終わりにしない。不足が審査判定なら store_review_readiness の SKILL.md を読み、素材の不足なら store_listing_pack の SKILL.md を読んで、その不足を埋めてからこのスキルへ戻り、提出を続ける。

- 前段へ戻る理由が、ユーザーや開発者でないと解消できない不足（署名、本人確認、支払い手段など）の場合だけ、該当スキルの手順書の形で渡し、その項目を未完了として追う。

- 進め方はストアごとに違うため、最初に [実行経路の振り分け](references/execution-routes.md) で、そのストアの経路（公式APIや自動化、ブラウザ操作、手作業のみ）を確定させる。経路が未確認のストアを、他ストアのやり方で進めない。

- ブラウザ操作は Chrome（クラウドブラウザ）を使う。他のチャットと共通の取り決めに従う。

## 絶対のルール（止まる場所）

- 次はユーザーの明示承認なしに実行しない。その場で止まり、内容を示して1つの選択として聞く。
  - 提出ボタンの確定（審査へ送る、公開する、価格を有効化する）
  - 支払い（開発者登録料、アプリごとの登録料、有料化）
  - 規約への同意、税務と銀行情報の送信、本人確認書類の送信
  - 既存公開アプリの削除、公開停止、価格変更、配信地域の縮小
  - 審査への返信文の送信（文案までは承認なしで作る）

- 下書き保存、項目の入力、素材のアップロード、入力内容の検証までは、承認済みの提出作業の範囲として進めてよい。ただし入力した内容は、確定前に一覧で確認できる状態にする。

- ログインは対象アカウントを先に照合してから行う。ブランドや開発者アカウントが複数ある場合は、画面上のアカウント名を必ず確認し、違うアカウントで下書きを作らない。認証コードは、コードの通知やメールが対象アカウント宛であることを確認してから使う。

- スキルだけでは対応できない部分を、無理に自動化しない。署名とビルド、証明書、ネイティブの開発者ツール操作、本人の端末でしかできない認証などは、最初から手順書側へ切り分ける。

- 鍵類はこのスキルの範囲に含めない。署名鍵とキーストア、証明書の秘密鍵、App Store Connect の APIキー（.p8）、Google Play のサービスアカウント鍵、鍵のパスワードなど、GitHub に上げられないものは、生成、保管、受け取り、署名や認証への使用のどれも行わない。必要になったら、手順書に手順と完了条件だけを含めて、開発者やユーザー本人が自分の環境で実施するよう促す。受け取るのは完了の報告（作った事実、保管場所、有効期限）だけで、鍵そのものや値を受け取らない。この線引きは、過去に鍵を扱った案件があっても今後の作業には適用する。

- 提出の状態を推測で報告しない。提出済み、審査中、リジェクト、公開済みは、管理画面または公式通知で確認したものだけを言う。確認できていないものは未確認と書く。

## 進め方

- パックの `07_submission/store-checklist.md` に、ストア別の作業票を作る。項目は、アカウント照合、下書き作成、ビルドの紐付け、素材と文案の入力、申告の入力、プレビュー確認、本人の承認、提出、審査状態の記録。

- ストアごとに1件ずつ完結させる。複数ストアを同じブラウザ作業で並行しない。アカウント取り違えと入力先の混同を防ぐためである。

- 入力はパックの正本からだけ行う。画面上でその場の判断で文案を変えない。変える必要が出たら、先にパック側を直し、差分を作業票に記録してから画面へ反映する。

- 提出前の最終確認では次を画面上で実見する。アプリ名とバージョン、価格と配信地域、スクリーンショットの並び、プライバシー申告の表示、審査用メモとデモアカウントの有無。

- 提出後は、提出日時、提出したバージョンとビルド、ストア側の受付IDや状態を作業票と台帳に記録する。審査結果の確認方法（どこを見れば分かるか）も同じ場所に書く。

## 手順書に切り分ける（開発者向け）

- 自動化できない、またはAIエージェントの環境ではできない作業は、[手順書テンプレート](references/manual-handoff-template.md) で手順書を作る。

- 手順書は開発者がそのまま実行できる粒度にする。前提、開く場所、操作の順番、各ステップの完了条件、詰まった場合の戻り方、完了したら何をどこへ知らせるかまで書く。知識がないと分からない箇所は、画面名と項目名を具体的に書く。

- 手順書で渡した作業は、完了の報告を受けるまで未完了として追う。完了条件（例：ビルド番号、アップロード完了画面、証明書の有効期限）を先に決め、報告と実物を照合する。

- 代表的な切り分け先は次。鍵類の生成と保管（署名鍵、キーストア、証明書の秘密鍵、APIキー、サービスアカウント鍵。範囲外として手順書で本人が実施する）、Xcode や Android Studio での署名とビルド書き出し、証明書とプロビジョニングの作成、開発者本人の端末での2要素認証、本人確認書類の提出、実機での最終動作確認。

## 審査結果とリジェクト対応

- 審査結果は [リジェクト対応](references/rejection-response.md) の手順で扱う。理由文を原文のまま記録し、分類（アプリ側の修正、申告の修正、説明で解けるもの、ポリシー解釈の相談）してから次の一手を決める。

- 返信文と再提出の材料はパック側へ反映してから送る。再提出で変えた点は、変更前と変更後が分かる形で作業票に残す。

- 同じ理由で2回落ちた場合は、3回目を同じ形で出さず、原因の仮説と別の解き方をユーザーと相談する。

## 報告して閉じる

- ストアごとに報告する。何を提出したか、現在の状態、次に起きること（審査期間の目安は公式案内ベースで、断定しない）、ユーザーがやること（1つだけ、または「なし」）。

- 報告と同じ作業で、対応する tracked item / goal の状態と活動を更新する。公開まで終わったら、その根拠（公開ページや管理画面の状態）を記録してから閉じる。

## Alternatives for better results

- 提出前の判定と不足の洗い出しは store_review_readiness スキルが担う。

- 素材の不足は store_listing_pack スキルで揃え直す。提出画面の前で場当たり的に作らない。

- 公開後の宣伝文や告知ポストは、このスキルでは扱わない。公開の事実確認までをこのスキルの範囲とする。
