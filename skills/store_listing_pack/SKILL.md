# ストア素材パック作成

## 概要（発動条件と3点セットの位置づけ）

- 提出に必要な情報を全ストア分まとめて、1つのフォルダに揃える専用スキル。「素材を揃えて」「申請用のフォルダを作って」「スクショと紹介文を用意して」で使う。

- 3点セットの2番目として使う。前提は store_review_readiness の入力リスト（素材パック用）。入力リストがない場合は、ユーザーへ差し戻さず、store_review_readiness の SKILL.md を読んで不足の洗い出しを先に行ってから、このスキルへ戻る。

## 連携と自動継続（1つ呼べば、依頼の範囲まで進む）

- スキルは自動で互いを呼び出す仕組みではない。連携は、この節の指示に従って前後のスキルの SKILL.md を読み、その指示で続行することで成立させる。

- 元の依頼が通し依頼（提出や公開まで含む）の場合は、パックの完成報告で終わりにしない。store_submission_ops の SKILL.md を読み、提出へ自動で続行する。止まるのは store_submission_ops の承認ゲートと、ユーザーや開発者でないと解消できない不足だけとする。

- 元の依頼が素材作成だけの段階依頼の場合は、パックを渡して止まり、提出は次の一手として提示する。分類の考え方は store_review_readiness の「連携と自動継続」と同じにする。

- 成果物は素材パック1フォルダだけにする。構成は [パック構成](references/pack-structure.md) のとおり固定し、アプリやストアが変わっても同じ形を保つ。提出実行（store_submission_ops）はこのパックだけを見て進められる状態にする。

- パックは提出先の数だけコピーを作らない。正本は1つとし、ストア別の差分はパック内のストア別フォルダと変換表で持つ。

## 絶対のルール

- 実物に基づかない素材を作らない。スクリーンショットは実際のアプリ画面から取る。存在しない機能、未実装の画面、他アプリの画面を素材にしない。

- 文章はマスター原稿を1つ作り、ストア別に文字数と形式だけを変換する。ストアごとに別々の主張や違う説明を作らない。変換で意味が変わる場合は、そのストアの版を差分として明示する。

- 寸法と文字数は推測しない。対象ストアの現在の仕様を [スクリーンショット仕様](references/screenshot-specs.md) と [文案の仕様](references/copy-specs.md) で確認し、パックの検証で実測する。仕様が変わっていたら references の数字も同じ作業で直す。

- 秘密情報をパックに入れない。デモアカウントのパスワード、APIキー、署名鍵は入れず、保管場所への参照だけを書く。スクリーンショットに個人のメールアドレス、トークン、実データが写っていないか1枚ずつ目視する。

- 鍵類の生成と保管もこのスキルの範囲に含めない。鍵が要る場面では、パックには保管場所への参照だけを置き、作り方と保管の手順は store_submission_ops の手順書側で本人が実施するものとして切り分ける。

- 著作権と商標を素材ごとに確認する。他者のロゴ、キャラクター、楽曲、フォントの利用可否が未確認の素材は、未確認として隔離し、提出用フォルダに入れない。

## パックを作る

- `~/workspace/custom-skills/store_listing_pack/scripts/scaffold_pack.py` で雛形を作る。引数はアプリのスラッグとバージョンと出力先。既存パックがある場合は上書きせず、差分だけを足す。

- マスター情報を `00_manifest.yaml` に集める。アプリ名、開発者名、カテゴリ、価格モデル、サポート連絡先、プライバシーポリシーURL、各ストアの登録IDへの参照、素材の完成状態。このファイルがパックの目次を兼ねる。

- 文案は [文案の仕様](references/copy-specs.md) に沿って作る。マスター原稿（長文の説明、短文の紹介、キーワード、更新内容）に、ストア別の整形版を添える。宣伝文句は実態を超えない。最上級や効果保証の表現は根拠がある場合だけ使う。

- 画像は次の順で揃える。
  1. アイコンの正本（最大サイズ、透過なし版を含む）
  2. スクリーンショット（実画面の撮影計画を先に作り、どの画面をどの順で見せるかを決めてから撮る）
  3. プロモーション画像（必要なストアだけ。フィーチャーグラフィック、プロモーションタイル等）

- スクリーンショットの撮影計画では、1枚目にアプリの核が伝わる画面を置き、個人情報を含まないデモデータで撮る。端末の時刻、通知、ステータスバーの不自然な要素を整える。装飾を足す場合は、画面そのものを改変しない範囲に限る。

- 申告材料をパックに入れる。データ棚卸し表、プライバシー申告の回答、権限ごとの理由文、年齢レーティングの回答、輸出コンプライアンス等の回答、審査用メモとデモアカウント参照。これらは store_review_readiness の成果と一致させる。不一致を見つけたら、どちらが実態かを確認してから直す。

- ビルド自体はパックに入れない。ビルドの置き場所、バージョン、ビルド番号、チェックサムへの参照だけを `05_build/build-pointer.md` に書く。

## 検証してから渡す

- `~/workspace/custom-skills/store_listing_pack/scripts/validate_pack.py` を実行する。自動で検査できるのは、必須ファイルの有無、画像の実寸と形式、文案ファイルの文字数一覧の出力、秘密情報らしき文字列の混入までとする。それ以上をスクリプトが検査したことにしない。

- 自動検証で拾えない項目を目視と実アクセスで確認する。文案の文字数と各ストアの上限との照合（スクリプトが出す文字数一覧と copy-specs.md を突き合わせる）、プライバシーポリシー等のURLが実際に開けるか、スクリーンショットの写り込み、全ストア分の文案の意味の一致、アイコンの小サイズでの視認性。

- 検証結果を `07_submission/pack-status.md` に書く。揃ったもの、不足、未確認、提出に使ってはいけない素材を分ける。不足があるまま「完成」と言わない。

- パックを渡したら、対応する tracked item / goal の状態も同じ作業で更新する。

## Alternatives for better results

- 不足の洗い出しと審査判定は store_review_readiness スキルが担う。

- パックを使った提出は store_submission_ops スキルが担う。

- スクリーンショットの見せ方や宣伝画像のデザイン改善は、実物に基づく範囲で media 生成と組み合わせてよい。ただし生成画像を実際の画面の代わりにしない。
