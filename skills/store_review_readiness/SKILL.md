# ストア審査準備

## 概要（発動条件と3点セットの位置づけ）

- アプリをストアに出す前の下準備専用スキル。「ストアに出したい」「審査に通したい」「申請の準備をして」「何が足りないか調べて」で使う。

- 対応ストアは広く取る。Apple App Store（iOS / iPadOS / macOS / watchOS / tvOS / visionOS）、Google Play（Android / Wear OS）、Chrome Web Store、Microsoft Store（Windows）、Microsoft Store 以外の Windows 配布、Firefox Add-ons、Microsoft Edge Add-ons、Samsung Galaxy Store、Amazon Appstore、Steam など。ユーザーが挙げていないストアでも、同じ手順で対象に加える。

- 3点セットの1番目として使う。順番は固定する。①このスキルで要件と不足を洗い出す → ② store_listing_pack で素材パックを1フォルダに揃える → ③ store_submission_ops で実際に提出する。

- このスキル自体の成果物は2つだけにする。審査準備レポート（ストア別の合否見立てと不足一覧）と、後続2スキルがそのまま使える入力リスト（素材パックに必要な項目、提出時に必要なアカウント・権限・判断の一覧）。ただし作業全体の終わりは、元の依頼の範囲で決める。詳しくは次の「連携と自動継続」を使う。

## 連携と自動継続（1つ呼べば、依頼の範囲まで進む）

- スキルは自動で互いを呼び出す仕組みではない。連携は、この節の指示に従って次のスキルの SKILL.md を読み、その指示で続行することで成立させる。リンクを置くだけで連携したことにしない。

- 開始時に、元の依頼を次のどちらかに分類する。
  - 通し依頼：「ストアに出して」「申請して」「公開まで」「提出を進めて」など、提出や公開まで含む依頼。このスキルが呼ばれた場合も分類は依頼全体で行う。
  - 段階依頼：「何が足りないか調べて」「審査準備だけ」「素材だけ揃えて」など、範囲が明示された依頼。

- 通し依頼の場合は、レポートを渡して終わりにしない。入力リストをそのまま渡して store_listing_pack の SKILL.md を読み、素材パック作成へ自動で続行する。素材パックが完成したら store_submission_ops の SKILL.md を読み、提出へ自動で続行する。各段階の途中で再度の許可は求めない。止まるのは store_submission_ops の承認ゲート（提出確定、支払い、規約同意など）と、ユーザーや開発者でないと解消できない不足だけとする。

- 段階依頼の場合は、その段階の成果物を渡して止まる。次の段階は、勝手に始めず、次の一手として提示する。

- 分類がどちらか判断できない場合は、提出確定などの不可逆な手前までは通しとして進め、承認ゲートで必ず止まる。段階をまたぐたびに、どのスキルへ移ったかを報告と作業記録に残す。

- アプリ本体のコード修正はこのスキルではしない。直すべき箇所は、場所と理由と直し方を特定してレポートに書き、開発者の作業として切り分ける。

## 絶対のルール

- 要件の数字を記憶で書かない。対象ストアの公式ドキュメントをその作業の中で開いて確認し、確認日と出典URLをレポートに残す。ガイドライン、SDK要件、対象APIレベル、手数料、スクリーンショット寸法は頻繁に変わるため、過去の案件の数字を流用しない。画面上のフォームと公式説明が食い違う場合は、画面側を正として記録する。

- 推測で「審査に通る」と言わない。判定は「提出可能」「直せば提出可能」「未確認」の3つだけを使い、根拠（実物確認、公式要件との照合、人間の動作確認のどれか）を添える。

- 秘密情報をレポートやパックに書かない。パスワード、APIキー、署名鍵、証明書の秘密鍵、デモアカウントのパスワードは置き場所（Secure Vault、1Password、開発者のMacなど）への参照だけを書く。

- 鍵類の生成と保管は、3点セット全体の範囲に含めない。このスキルでは有無と保管場所の確認までを行い、不足していたら「本人が手順書で実施する項目」として分類して store_submission_ops へ渡す。鍵そのものを新たに作ったり、預かったりしない。

- 支払い、開発者登録の完了、規約への同意、提出ボタンは、このスキルでは実行しない。必要な場面を特定して store_submission_ops の手順書側へ渡す。

## 始める前にアプリの実態を読む

- 対象アプリのリポジトリ、README、設計資料、ビルド設定、依存ライブラリ一覧を読む。読めない場合は、読めた範囲と未確認の範囲を分けて記録する。

- 次を短く確定させる。確定できない項目は不足として扱う。
  - 対象プラットフォームと配布したいストア（複数可、優先順位つき）
  - アプリが実際にすること、主要機能、ログインの要否、サーバー通信の有無
  - 収集・送信するデータの実態（自分のコードだけでなく、解析、広告、クラッシュ送信、AI連携など第三者SDK分を含む）
  - 使っている権限と、その権限が要る機能との対応
  - 課金の有無（アプリ内課金、サブスクリプション、外部決済、広告、アフィリエイト）
  - 対象年齢、ユーザー生成コンテンツ、チャットや外部リンクの有無
  - 動作に必要なアカウント、特殊なハードウェア、地域や時刻への依存など、審査員が再現できない条件の有無

- 既存の公開ページや前回のリジェクト履歴がある場合は、先に読む。前回と同じ理由で落ちる提出を繰り返さない。

## ストア別に要件を調べ直す

- ストアごとに [ストア別要件マトリクス](references/store-matrix.md) の観点で公式要件を確認し、そのストア専用の行を作る。観点は、アカウントと費用、本人確認と税・銀行情報、提出物の形式、技術の下限（SDK、対象API、Manifest版など）、プライバシー申告、年齢レーティング、課金ルール、審査の特殊条件（クローズドテスト期間など）、審査期間の目安。

- 調べた要件は「全ストア共通」と「そのストアだけ」に分ける。共通の不足をストアごとに重複して数えない。

- 新しいストアを初めて扱う場合は、マトリクスにそのストアの行を追加してから判定を始める。行がないストアについて、他ストアの要件で代用しない。

## 審査落ちのパターンを先に潰す

- [リジェクト頻出パターン](references/rejection-patterns.md) と照らし、対象アプリに当てはまるものを全て挙げる。特に次は毎回必ず確認する。
  - 実態と申告の不一致（プライバシー申告、権限の理由、スクリーンショット、説明文が実際の動作と違う）
  - 最小機能の不足、Webの包み直しだけのアプリ、テンプレート量産と見える作り
  - ログイン必須なのに審査用アカウントや操作説明がない
  - クラッシュ、未完成画面、ダミー文言、リンク切れのまま提出している
  - 外部決済への誘導、ストア課金の回避と読める導線
  - 権限の過剰要求（使っていない、理由を説明できない権限が残っている）

- 当てはまった項目は「提出前に必須で直す」「提出はできるが落ちる確率が高い」「審査員の質問で止まる恐れがある」の3段階に分ける。

## 下準備と調整を計画する

- [審査準備チェックリスト](references/readiness-checklist.md) を案件用に複製し、項目ごとに状態（済み、不足、不要、未確認）と担当（AIエージェント、開発者、ユーザー本人）を付ける。

- 調整は次の順で並べる。上の段が終わらないと下の段の判定ができないためである。
  1. アカウントと契約（登録、本人確認、規約、税と銀行、有料アプリ契約）
  2. アプリ側の技術要件（SDKと対象API、署名、権限の削減、プライバシーマニフェスト等の同梱ファイル）
  3. 申告の実態合わせ（データの棚卸し、プライバシー申告の下書き、権限ごとの理由文）
  4. 審査の再現性（デモアカウント、審査用メモ、特殊条件の代替手順）
  5. ストアページの下書き材料（これは素材パック側の入力リストとして渡す）

- 開発者でないと直せない項目は、その場で手順と完了条件を書く。store_submission_ops の手順書に転記できる粒度にする。

## 成果物を渡す

- 審査準備レポートには次を含める。ストア別の判定と根拠、必須で直す項目（担当つき）、公式要件の出典と確認日、未確認の範囲、後続スキルへの入力リスト。

- 入力リストは2つに分けて明示する。素材パック用（アプリ名、紹介文、スクリーンショットなど揃える物の一覧）と、提出実行用（必要なログイン、アカウント権限、支払い、本人の判断が要る場面の一覧）。

- レポートを渡したら、対応する tracked item / goal の状態も同じ作業で更新する。

## Alternatives for better results

- 素材を揃える段階では store_listing_pack スキルを使う。

- 実際に提出する段階では store_submission_ops スキルを使う。

- アプリのコンセプトや体験そのものの見直しが先に必要な場合は concept-driven-ux スキルを先に使う。
